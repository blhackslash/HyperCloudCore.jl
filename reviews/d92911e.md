## Findings

### F1 (low/medium, CONFIRMED) — with `volume_estimator`, the interior `Σ V U` is not exact next to walls; the new docs say it is
`src/Grid/Adaptivity.jl:215-217` (`_reestimate_volumes!`: `ε = total_mass(pg)` before − after `update_volumes!`),
`docs/src/particle_grids/volumes.md:79` ("Σ V U over the interior (and over all particles) is preserved exactly").
The remap itself is now exact over the interior (probe: ≤ 3e-16). But with `volume_estimator` set (the builders pass it
on moving grids, i.e. the main use of adaptivity), `_reestimate_volumes!` re-estimates **all** volumes, ghosts included
(the new particle changes the ghosts' Shepard volumes), and `total_mass` counts the ghosts. The ghosts' content change
`Σ ΔV_g U_g` therefore enters `ε` and is put onto the interior particles of `changed` (ghosts are no longer in it after
d92911e). Result: total including ghosts exact, interior off by exactly minus the ghost change.
- Scenario (`probe_adapt_walls.jl`, last block): 1-D/2-D FixedDirichlet box, n = 20, 45 % jitter,
  `ParticleAdaptivity(; volume_estimator = ShepardVolumes())`: interior content changes by +6.5e-4, −2.6e-3 (1-D),
  +9.5e-4, +1.1e-3, +4.7e-4 (2-D) relative to `Σ V|U|`, with `d_gh = −d_in` and `mass_residual` ≈ 1e-16. Ghost
  states stay untouched (good).
- Pre-existing mechanism (before d92911e part of `ε` went to the ghosts' states instead), but it now contradicts the
  new statement and the goal of the fix; on a walled moving grid each event near a wall moves ~1e-3 of the mass across
  the wall.
- Fix: compute `m_remap` and `ε` over the interior only (`Σ_{!is_boundary} V U` before/after the re-estimation), so the
  ghosts keep the content change of their own volumes; then decide what `mass_residual` reports (interior change, or
  document that `total_mass` changes by the ghost-volume part). Otherwise restrict the volumes.md sentence to calls
  without `volume_estimator`. A regression test: the d92911e wall test with `volume_estimator = ShepardVolumes()`
  checking `content(false)`.

### F2 (low, CONFIRMED) — the snap tolerance is unbounded and can snap the neighbour of a wall point onto the wall
`src/Grid/Domains.jl:222-223`. The new term `8 eps(T) (|canvas_min| + canvas extent)` grows with the number of
points per axis and with the offset of the domain; in Float32 it reaches `dx/2` from `(|cmin| + L)/dx ≈ 5.2e5`.
- Scenario: Float32 `[0, 1]`, `Ns = 1_000_000`: tolerance 0.954 dx, the lattice point next to `x = 1` is put on the
  wall too → **two interior particles at x = 1.0** (`probe_snap_dup.jl`; zero distance in the neighbour lists, a merge
  event, a duplicated wall). Ns = 6e5/8e5 are still fine (0.57 dx, no duplicate). Offset Float32 domains get there
  much earlier: `[100, 101]` with Ns = 1e4 → 0.964 dx, `[1000, 1001]` with Ns = 1e3 → 0.955 dx (no duplicate in
  these runs only because the lattice round-off happened to stay below the margin). The commit message's "still far
  below dx" holds for the probed range (2 % at Ns = 20000 on [0, 1]) only. Float64: irrelevant (1.7e-8 dx at 1e6).
- Before the fix the failure mode was a lost wall point; now it is a duplicated one, at far more extreme sizes (in
  Float32 the coordinates themselves resolve only ~dx/10 there), hence low.
- Fix: cap the tolerance (`min(…, dx/4)`), or better set the wall points by index:
  `k = round(Int, (maxs − canvas_mins)/dx)` (and the analogue for `mins`) and assign `x = maxs` for `I[d] − 1 == k`,
  which needs no tolerance at all.

### F3 (low, CONFIRMED) — `eps(Float64)` literal in the ghost-layer guard; ineffective in Float32
`src/Grid/Domains.jl:164`: `ceil(Int, interp_range_factor * (max_dx / dxs_f[d]) * (1 - 4 * eps(Float64)))`. Violates the
repo rule "no Float64 literals in numerics, use eps(T)". In Float32 the product is a Float32 value 1–2 ulps above an
integer, and the Float64 factor (1 − 9e-16) cannot pull it back: in a sample of 3820 Float32 configurations
(`dx_max = 1/n`, ratio 2…6, R/dx_max ∈ {2, 2.5, 3, 3.5}) 134 got one layer more than ⌈R/dx_d⌉ (e.g. n = 197, ratio 6,
3.5 → 22 instead of 21). Harmless (a few more ghost particles), but the guard does not do what it says. Fix:
`(1 - 4 * eps(T))` with the product in `T`, or compute `ceil(Int, R / dx_d - 4eps(T) * R / dx_d)` directly from `R`.

### F4 (low, docs, CONFIRMED) — the muscl.md limitation numbers hold for the cached CFL path only
`docs/src/spatial/muscl.md:78-87`. The stated Σ|c_ij|Δx values (MUSCL3 R = 2.5Δx: 1.500 vs 0.644; MUSCL5 R = 3.5Δx: 1.6×
smaller; MUSCL5 R = 2.5Δx: 1.475 vs 1.500) are exactly what the **cached** weights give (`probe_muscl_cfl.out`). The
uncached path (`cached_weights = false`, and every call before the first right-hand side, i.e. the first step)
factorises the Taylor fit of `_divergence_degree`, which for MUSCL5 gives 1.167 (R = 3.5Δx) and 1.500 (R = 2.5Δx),
i.e. the fit in use: the first step's Δt is 1.57× larger than the following ones for MUSCL5, R = 3.5Δx. For MUSCL3
both paths give 1.500. Suggest one sentence: "the numbers are those of the cached weights (every step after the
first); the uncached estimate uses the Taylor fit and for MUSCL5 coincides with the fit in use". Related wording: the
`get_time_step` docstring (`src/Grid/ParticleGrids.jl:368`) calls the cached weights "the weights in use", which the
new note says they are not where the safeguard lowers the degree.

## Test coverage

Well covered by the new tests: the wall remap (ghost dict equality, interior content, global bounds), the slot
prediction (exact count) and the frozen-slot `CapacityError` with an untouched grid, the anisotropic band depth, Float32
wall snapping up to Ns = 20000, VK in Float32, the safeguard (consistency for F = x, Upwind with one neighbour), the
`a = 0, b ≠ 0` tableau, the non-commuting IMEX order test. Each fails on the code it fixes.

Missing / weak:
- The anisotropic test compares neighbour counts only for `dx = (0.1, 0.05)` and only for two particles; the
  `(0.02, 0.01)` case checks the band depth only (R = 0.05 = 5 dy has distance ties). Worth adopting:
  `probe_ghost_band.jl` reduced to one 2-D and one 3-D case (all interior particles against the analytic count, R
  without ties; < 2 s).
- No Float32 and no 2-D test of the wall remap, and none with `volume_estimator` (F1). `probe_adapt_walls.jl` with one
  seed per case (~10 s incl. compilation) covers all three and would catch F1 once fixed.
- `_slots_after_events` is tested on one 1-D insertion; a 2-D merge+insert case with slot-major layout
  (`probe_slots.jl`, one seed) is cheap.
- No test of the snap tolerance against duplicates (F2), e.g. "minimum spacing > dx/2 and Ns+1 interior points" for a
  Float32 grid with a large |x|/dx (a 1-D Float32 grid on `[100, 101]` with Ns = 1e4 is fast).

- `test/unit_schemes.jl` "Central/Upwind" testset is 1-D only; a 2-D particle with exactly `B(2, q)` neighbours is
  not covered (low risk, the check is dimension-generic).

  warning the converted case gets; harmless, maybe worth the same warning.

  irrelevant next to the remap.

## Verdict

The fix round is correct and complete for every addressed item; each change comes with a regression test that fails on
the old code, and the numerics claims in the commit messages reproduce (Central4 orders, IMEX EOCs, VK accuracy, exact
slot prediction, ghost-band completeness in 2-D/3-D). The wall remap now keeps boundary data intact and the interior
sum exact, and the touched kernels (VK limiter, Central/Upwind, adaptivity pre-check) agree between KA CPU and
Polyester in Float64 and Float32. Remaining: with a `volume_estimator` the re-estimation still moves the ghosts' volume
change into the interior, contrary to the new docs (F1); the unbounded snap tolerance can duplicate a wall particle at
extreme Float32 resolutions (F2); a Float64 literal in the ghost-layer guard (F3); and a docs precision issue about the
CFL paths (F4). Full suite 969/969.

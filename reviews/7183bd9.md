## Findings

### F1 (low, CONFIRMED) — `_wall_index` tolerance: a fixed 0.01-spacing floor that is not round-off, and no term for the round-off of `canvas_min`
`src/Grid/Domains.jl:190-194`: `abs(r - k) <= min(T(0.25), T(0.01) + 8 * eps(T) * abs(r))`. The comment says the
ratio carries "a few ulps of the ratio" of round-off; the tolerance does something else on both ends:
- **Snapping of near-multiples (behaviour change).** In Float64 the round-off of `r` is ~1e-15 r, but every wall
  within 0.01 dx of a lattice point is now snapped: `[0, 1]` with `dx = 1/(n + f)`, \|f\| < 0.01, moves the whole wall
  plane by \|f\| dx, and for f < 0 (lattice point just outside the wall) the interior gets one extra row: n = 30,
  f = −0.009 → N_interior 31 (old 30), the last spacing 0.991 dx (`probe_wall_index.jl nondiv`). For a rounded user
  spacing (e.g. `dx = 0.03333` on `[0, 1]`, L/dx = 30.003) this is arguably what one wants, but it is not
  documented (neither the `get_points` docstring nor the test, whose comment says a wall between two lattice points
  "is not snapped to") and changes N and results of such configurations versus 0.7.9. Divisible extents are
  unaffected (96/96 standard grids bitwise identical).
- **Not enough for the `canvas_min` term in Float32.** `r = (w − canvas_min)/dx` carries the rounding of
  `canvas_min = mins − N_ghost dx`, i.e. up to `ulp(canvas_min)/(2 dx)`, which the `8 eps r` term does not cover when
  `r ≈ N_ghost` (the `mins` wall). For walls at negative powers of two `canvas_min` lies in the next binade:
  `[-1, -0.7]`, Ns = 1e5: `r_lo = 2.98023`, tolerance 0.0100 → index −1 → no point on the wall; 86/637 Float32
  configurations with lo ∈ {−0.5, −1, −2, …} and ulp/dx < 0.1 (`probe_wall_pow2.jl`). The lattice point then sits
  0.014–0.046 dx inside (rounding happens to go inward there), so nothing is lost or duplicated (0/637 lost, 0/637
  dup; positive lo / negative hi walls: 0/388 affected), but the wall particle is not on the wall, which is what the
  snap exists for. The old distance tolerance had the `8 eps(|canvas_min| + extent)` term and put these on the wall.
- Fix: derive the tolerance from the actual round-off and drop the constant floor, e.g.
  `tol = min(T(0.25), (2 * (eps(abs(w)) + eps(abs(canvas_min))) + eps(T) * abs(w - canvas_min)) / dx + 4 * eps(T) * abs(r))`;
  if snapping near-multiples is intended, keep a floor but say so in the `get_points` docstring and in a test.

### F2 (low, CONFIRMED) — two new regression tests do not fail on the code they fix
- `test/unit_core.jl:162-172` (Float32 offset walls, d92911e F2): `[100, 101]`, Ns = 1e4 and `[1000, 1001]`,

### F3 (low, CONFIRMED) — the shock-band and DMP-threshold changes have no test
Both changes are correct and fix real behaviour, but no test fails on the old code:
- Shock band (`src/Grid/Adaptivity.jl:336-340`): with the 4R band the old code accepts, in 2-D, an insertion whose
  centre is 4.01 R from a reduced-order particle and changes that particle's state (ΔU = +2.4e-6); the new band
  (4.73 R for R = 2.5 dx) excludes it (`probe_shock_band.jl`). The existing "No events inside the shock band" test is
  1-D, where the band is unchanged.
- DMP threshold (`:617-622`): a Float32 set with V = 1e-6 and a 10 % overshoot lost 3.0 % of its content on the old
  code (excess below the absolute `eps(T)`), exact now (`probe_dmp.jl`).
- Fix: add both as small tests (the DMP one is three lines next to "DMP repair is conservative"; the band one a 2-D
  periodic 40² grid, one particle with order 1 and a hole/close pair ≈ 4.1 R away; ~2 s, reuses existing types).

### F4 (low, CONFIRMED) — the larger band makes the shock-band marking 2.2× slower in 3-D
`_detect_events` marks the band with one `_collect_near!` of radius `band` per reduced-order particle. In 3-D the band
grows from 4 R to `R(1.5 + 2√3) + dx` = 5.36 R (R = 2.5 dx), i.e. 2.4× the volume: 98 → 215 ms per call at
N = 32768 with 3072 reduced particles (2-D N = 40000: 7.6 → 9.0 ms; `probe_band_cost.jl`). It only runs when
`_has_adapt_candidates` finds something, and is host-serial like the rest of the event work, so this matters on large
3-D runs with shocks only. Suggestion (not needed for correctness): invert the test — for the few particles that
would start an event, check whether a reduced-order particle lies within `band` (one `_collect_near!` per candidate
instead of per reduced particle).

### F5 (low, CONFIRMED) — semantics change of `mass_residual` / `total_mass` on walled moving grids, and the conserved quantity is private
Correct by design and documented (`adapt_particles!` docstring, volumes.md), but a behaviour change for existing users:
with a `volume_estimator` on a grid with walls, `total_mass` now changes by the ghosts' content change at every call
with events near a wall (probe: −1.2e-3…+2.6e-3 of `Σ V|U|` per call, Shepard; previously exact to 1e-16), and
`mass_residual` reports the interior change instead of the `total_mass` change. Downstream diagnostics that compare
`total_mass` before/after (HyperCloudCore's own `test/SimulationFunctions/direct.jl` `discrete_mass_error`;
`Simulations/tools/adapt_study.jl`, whose header documents `mass_residual` as "change of Σ V_i U_i over the call" and
whose per-step accounting uses `total_mass`) will now attribute that ghost part to the step. The quantity that is
conserved (`_interior_mass`) is internal, so users cannot measure it without re-implementing it. Suggestion: mention
the change in the release notes; consider exporting an `interior_mass(pg)` (a public API addition, the user's call) and
using it in the diagnostics on walled grids.

## Minor issues

- `ExponentialWeightFunction(1, 2)` / `InverseWeightFunction(1, 2)` (two `Int`s) still give `T = Int`: the first throws
  `InexactError` (`inv_range_sq = 0.25`), the second fails at evaluation (`Int(1e-12)`). Pre-existing; promoting with
  `float` (`promote(float(alpha), float(range))`) in the `Real, Real` methods would make the new "promoted to a common
  type" statement hold for integers too.
- `_check_starved` (`src/Grid/ParticleGrids.jl:281-288`): `D + 1` matches the intercept fits (Central, MUSCL); the
  Tiwari upwind fit needs only `D`, so the message "(frozen or first order)" can be a false alarm for that scheme with
  exactly `D` neighbours. It also runs only at construction; a moving grid that starves later is not reported.
  Both fine for a configuration hint.
- `_dmp_repair!`: when `abs(excess)` is below the threshold the clipped values stay clipped and the excess is dropped
  (≤ 4 eps · scale). That is round-off of the set's content, consistent with the tests' 1e-13 · scale tolerances; just
  noting that "skips" in the commit message means "drops".
- `docs/src/particle_grids/volumes.md`: "(Up to version 0.7.9 …)" — Project.toml is at 0.7.9 on this branch, so the
  sentence is right only once the next version is tagged; fine if the bump follows before release.
- The commit message of 7183bd9 lists "complete stencils on anisotropic 2-D and 3-D lattices" and "the Float32 layer
  count" under tests; the latter does not test what it says (F2).

## Verdict

The change set is correct: the interior content is now exact with a volume estimator next to walls (verified with
Shepard and MLS estimators in Float64 and Float32), periodic grids and calls without an estimator are bitwise unchanged,
wall points are chosen by index with no lost or duplicated wall point in ~6000 Float32/Float64 configurations (52
duplicates on the old code), the Float32 ghost guard and the relative DMP threshold fix what they claim, the 2-D/3-D
shock band now covers the remap reach, and the minors are addressed accurately. Full suite 996/996, no warnings.
Remaining: the wall tolerance's constant 0.01 floor snaps near-multiple extents (undocumented behaviour change) while
missing the `canvas_min` round-off for Float32 walls at negative powers of two (F1); two of the new regression tests do
not fail on the old code (F2); the band and DMP changes are untested (F3); the band marking is 2.2× slower in 3-D (F4);
and walled moving grids now see `total_mass` drift by the ghosts' content change, with the conserved quantity private
(F5, by design, needs a release note).
Findings: 0 high, 0 medium, 5 low (F1–F5); all confirmed (the device path of `_interior_mass` by reasoning only).

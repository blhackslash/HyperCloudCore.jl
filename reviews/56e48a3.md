## Findings

### F1 (low/medium, CONFIRMED) — the relative limiter tolerance lets Float32 reconstructions go negative at near-vacuum minima
`src/Interpolation/Limiter.jl:79`: `tol_m = 16 eps(T) max(|f_i|, u_max − u_min)`. An increment pointing to the lower bound
is skipped (not limited) while `|δ| ≤ 16 eps · range`, even when `f_i − u_min` is far smaller than that. At a particle
that is (nearly) the local minimum, `f_i ≈ u_min ≈ 0`, next to O(1) data, round-off-level gradients then take the
interface value below `u_min` and below zero. In Float32 the band is `1.9e-6 · range`; the old absolute `1e-12` limited
these increments.
- Direct call: Float32 `f_i = u_min = 1f-8`, `u_max = 1`, `δ = −1f-7` → `φ = 1`, interface value −9e-8 (old: `φ = 0`,
  value 1e-8). Float64 `f_i = 1e-17`, `δ = −1e-15`: −9.9e-16 (old code the same).
- Through `update_content!` (`probe_vacuum_f32.jl`): 1-D Float32 lattice, `u = 1e-9` at every 7th particle, `u = 1`
  elsewhere, MUSCL2 with BJ or VK (hard): N = 100: 22 negative interface values (undershoot 4.2e-7), N = 400: 30
  (1.7e-6), N = 1000: 82 (1.5e-6); **old code: 0 in every case**. Float64 (dips 1e-18): 6–10 negatives ≤ 3.2e-15
  (old: 6–72, ≤ 8.2e-15, i.e. the F64 hole is smaller than before). MUSCL3: none either way.
- Consequence: a negative interface density/pressure goes into the numerical flux (for Euler a NaN sound speed in
  `max_eigenvalue`, unless the physics clamps it); MOOD PAD only sees the candidate afterwards. Float32 is the GPU
  configuration of the Euler benchmarks, where positivity round-off was already an issue. The scenario needs a
  near-zero slope at an isolated low particle (lattice symmetry), so it is narrow; the trade is otherwise an
  improvement (F64 and scale invariance).
- Fix (checked in `probe_vacuum_fix.jl`): make the tolerance relative to `f_i` and the bound the increment points to,
  `bound = δ > 0 ? u_max : u_min; tol = 16 eps(T) max(|f_i|, |bound|); r = (bound − f_i)/δ`. With `u_min ≥ 0` this
  keeps `f_i + δ ≥ f_i (1 − 16 eps) > 0`; O(1) flat regions keep the same `16 eps` tolerance; the VK box stays bitwise
  scale invariant; 0 negative interface values in all F32/F64 cases above. Add the Float32 dip as a regression test
  (it fails now, < 1 s).

### F2 (low/medium, CONFIRMED) — the `get_time_step` warning fires for a case HyperCloud documents as valid; its test passes only by order
`src/Grid/ParticleGrids.jl:403-406`. HyperCloud's driver treats an infinite CFL step as "no wave moves, go to tmax"
(`HyperCloud.jl/src/time_integration.jl:161-163`) and stops itself on non-finite states; `test/sims.jl:94-98` asserts
that a zero-velocity run "reaches tmax without a warning" (`!any(l -> l.level >= Warn, logs)`).
- Evidence (`probe_hc_zero_velocity.jl`, fresh session, HyperCloud against the branch): the run reaches tmax and
  logs `get_time_step: no particle restricts the time step …`; the assertion is false. In HyperCloud's suite it
  should still pass, but only because the NaN-state test just before (`sims.jl:85-87`, NaN wave speeds are skipped,
  so `get_time_step` returns `Inf` there) consumes the once-per-session flag first (by reading the test order; not
  run).
- The message also misnames the most common cause: for a NaN state `sum_c > tol` is false, so the particle is
  skipped and the step is `Inf`. The text only mentions zero wave speeds or missing fits.
- Fix: either leave the reporting to drivers (document `Inf` and drop the warning; HyperCloud already handles all
  three cases), or warn only for the broken case (interior particles with neighbours whose fit failed: e.g. write a
  sentinel for `!ok` in `_cfl_body!`, or count them), not for zero or non-finite speeds; at least name NaN states in the
  message. If it stays, HyperCloud's test needs a reset of `HyperCloudCore._WARNED_INF_DT` and a changed expectation.

### F3 (low, SUSPECTED) — `_count_inadmissible` on device arrays is not verified
`src/TimeStepping/TimeSteppers.jl:478-483`: `sum(Broadcast.instantiate(Broadcast.broadcasted(f, view(is_boundary, 1:N), view(U, 1:N))))`.
`view` of a `Growable` forwards to the held array, so on AMDGPU this is a reduction over a `Broadcasted` with the
ROCArray style and a closure capturing `eq`. GPUArrays is expected to handle such lazy reductions, but nothing here
checks it: the device suite (`test/gpu_tests.jl`, which runs MOOD U1/U2 on device, so it would exercise the
reduction) cannot run in this container, and the CPU/KA tests use host arrays. Every other reduction in the stepper
is `any`/`count` over a device view (`detect_and_drop!`).
- Cost on the host is negligible (`probe_count_cost.jl`: 0.29 % of an RK3 step with 4 checkpoints at N = 4e4 and
  4.9e5; serial, 624 bytes allocated per call).
- Fix: run `HYPERCLOUD_BACKEND=amdgpu julia --project=test/gpu test/runtests.jl` before merging. If it fails, use a
  kernel writing `!is_boundary[p] && !_admissible(eq, U[p])` into `work.scratch` and `count(view(scratch, 1:N))`,
  the same pattern as the existing reductions.

### F4 (low, docs, CONFIRMED) — the WENO scale-invariance statement holds in Float64, in Float32 only above |u| ≈ 1e-13
`src/Interpolation/WENO.jl:107`, `docs/src/spatial/weno.md:29`. `ε = 1e-12 max(u_i², IS_C) + floatmin(T)`: in Float32
`1e-12 u²` reaches `floatmin(Float32) = 1.2e-38` at |u| ≈ 1e-13 and is subnormal below that, so `floatmin` dominates.
- Evidence (`probe_scale.jl`): Float32 WENO2 box/Gauss scaled by 2^-50 (height 8.9e-16) differ from the scaled O(1)
  run by 4.9e-5…1.3e-4 (relative to the peak). Float64 is bitwise at 2^-50 and 2^-100, as are all Float32 limiters.
  The docs example "a profile of height 1e-13" is just at the Float32 edge. (Theoretical side note: in Float32,
  `f_i * f_i` overflows for |u| > 1.8e19, giving `e_tol = Inf` and `q = NaN` for a flat field; the old absolute offset
  stayed finite there.)
- Fix: qualify the docs sentence ("bitwise in Float64; in Float32 down to |u| ≈ 1e-13"), or compute `q` from the
  indicators normalised by `s² = max(u_i², IS_C)` (`ε/s² = 1e-12`, plus `floatmin` only when `s = 0`). That is scale
  free down to the underflow of `IS` itself and cannot overflow.

No other defects found in the diff. Checked and fine:
- **1-D limiters** (`Limiter.jl:173-205`): nearest-neighbour selection is unchanged (strict `<`, first wins, `iszero` as
  the sentinel). `sL/sR` with both non-zero and of equal sign gives a positive ratio or `+Inf`, so `limiter_phi` gives 1
  (minmod) or 2 (superbee), with no NaN. When `sL/sR` underflows to 0 the slope becomes 0, as minmod should. The old
  `|sR| < 1e-12 → r = 1` branch is gone, which only changes slopes below 1e-12. Bitwise scale invariant, F32 too.
- **UpwindFlux**: `√ε max(|u_L|, |u_R|)` is the right crossover (secant error `ε|F|/|Δu|` against Jacobian error
  `f''|Δu|/2`). Exactly equal states, `u = 0` included, take the Jacobian. A sonic pair (−1e-9, 1e-9) takes the secant
  (s = 0, Murman–Roe), as before. Using `u_L` only is asymmetric, but the pair defect is at round-off level
  (≤ ε|u|² in F32).
- **Praveen**: `det/tr² ∈ [0, 1/4]` for the SPD 2×2 moment matrix; the cut-off is a condition number of about
  1/(4ε). This is dimensionless and works for `InverseWeightFunction` units. `hyp ≤ ε·scale` is harmless.
- **WENO weights**: `1/(1 + q²)` is algebraically the old `β_S/(β_S + β_C)`. Zero indicators give w = ½ and a zero
  central indicator gives `w_S = 0`, with no NaN either way. At O(1) the results match the old ones apart from the
  tails, where the undershoot drops.
- **Starved MUSCL** (`MUSCL.jl:354-357`): the loop needs `basis_count(D, p−1)` neighbours for a degree `p−1` fit
  through the particle, as the test says (2-D: 2/5/9). The flux pass lowers the divergence entry by the neighbour
  count anyway (`_divergence_index`). Intermediate orders take the dynamic fit (the cached weights only serve
  `p == MAX_ORDER`). MOOD can still lower them further, and the order is only ever lowered in `particle_orders`
  (no race: per-particle write). In the probe the smooth error drops 36× where the stencils are starved.
- **`ssp_coefficient`**: the lookup applies only to non-Float64 explicit tableaus. It compares `a_t, b_t, c_t` after
  rounding the Float64 original, and the stage count first. A hand-made copy of a built-in gets the exact coefficient,
  which is correct. Only the constructor calls it. The 1.5082 vs 1.5032 difference changes the checked substep by
  0.3 % (`Δt/C`).
- **Zero-diagonal warning**: no built-in IMEX tableau (IMEX Euler, ARS222/233, PRSSP3, SSP2332) has an all-zero
  diagonal, so there are no false positives. A strictly lower `a` correctly warns, since it is evaluated explicitly
  in `_stage_implicit_rhs!`.
- **MOOD count**: when `detect_and_drop!` returns `false`, every inadmissible interior candidate is at order 1. PAD is
  always part of `_mood_flag!` when `eq` is given, and non-dirty particles kept a candidate checked earlier. So the
  count is exactly the order-1 inadmissible set of the accepted candidate. That is the substep when substeps are
  checked. Reset per step, warned once per stepper, skipped for `NoMOOD`.
- **Minmod/Superbee constructor check**: HyperCloud's inbuilt minmod methods are config dicts. A 2-D run now fails
  at build time instead of at the first right-hand side, so the behaviour is the same, only earlier.
- KA rules: no allocation, no `Float64` literal, no `T` from an enclosing method in the changed kernel paths
  (`_update_phi`, `_same_sign`, WENO, UpwindFlux, `update_content!`). The KA CPU parity tests in backends-a/b cover
  Minmod, VK, WENO2 and UpwindFlux, and they pass.

## Minor issues

- MOOD warning (`TimeSteppers.jl:558`) and `mood_inadmissible` docstring: "e.g. a CFL number above the positivity
  limit". On jittered clouds a first-order MUSCL with `RusanovFlux` is not positive at any CFL. With `U ≥ 0`
  admissible the count grows from 11 to 637 per step at CFL 0.1, min −1.1e-6 (`probe_inadm_roundoff.jl`). Also, with
  substep checks the counted state is the Euler substep, not the state the step continues with, so the docstring's
  "the step goes on with the inadmissible state" is not exact there. Suggest naming the scheme (non-aligned
  dissipation on irregular clouds) as a second cause and saying "candidate (or Euler substep)".
- `_WARNED_INF_DT` is global and once per session. In a long PDEStudio session only the first unbounded step is ever
  reported, and tests have to reset an internal global.
- `get_time_step` keeps an absolute cut-off `sum_c > T(1e-14)` (units 1/time). It is the same class as F7 but out of
  this change's scope. A relative form such as `sum_c > 0 && isfinite(1/sum_c)` would do.
- CLAUDE.md asks numerics changes to state the error before and after in the PR. The commit messages give it only for
  the EOC test. Numbers from the probes that could be used: O(1) results unchanged to ≤ 5e-12 in Σ|u|; VK overshoot
  8e-13 → 2e-16 on a Gaussian; WENO2 box undershoot −4.6e-8 → 0; starved MUSCL4 (R = 1.6Δx, 2-D) L2 1.57e-2 → 4.4e-4.
- Starved particles now use exactly determined reconstruction fits (e.g. 5 neighbours for degree 2 in 2-D). Unlimited,
  this overshoots more on a box (1.346 vs 1.053 at R = 1.6Δx). With a limiter the result is the same as MUSCL3. It is
  expected behaviour, but worth a docs sentence next to the starved-order note.
- `_count_inadmissible` allocates about 620 bytes per call on the host (the `Broadcasted` and its closure), four
  times per step. That is negligible, but it is an allocation in the stepper loop.

## Verdict

The change set does what it claims. In Float64 the limiters, WENO weights and upwind flux are now scale invariant,
bitwise for power-of-two scales and also in 2-D and on jittered clouds. Results at O(1) are unchanged or slightly
cleaner, the starved MUSCL order is a clear accuracy gain, and every fix has a regression test that fails on the old
code. Full suite 1021/1021, with no new warnings in the existing runs.

Two points to settle before merging:
- The new limiter tolerance opens a small positivity hole in Float32 at near-vacuum minima (F1). A one-line change of
  the tolerance closes it and keeps the scale invariance.
- The `get_time_step` warning contradicts HyperCloud's documented zero-velocity behaviour. HyperCloud's own test
  would catch it if it ran alone (F2).

Also open: the device path of the new MOOD count is unverified (F3), and a docs qualification for Float32 WENO (F4).

Findings: 0 high, 0 medium, 4 low (F1 and F2 low/medium, F3, F4 docs); 3 confirmed, 1 suspected.

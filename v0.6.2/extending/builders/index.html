Config-Driven Builders

The build_* functions in src/Builders/ turn flat, namespaced parameter dictionaries into the numerical objects of the package. It exists so that a wrapper (or a test suite) does not have to re-implement the symbol-to-type mapping for every scheme, tableau, limiter and strategy, and so that this mapping is updated together with the types it names.

using HyperCloudCore

context = Dict{Symbol, Any}(:Type => Float64, :D => 1, :M => 1, :Equation => eq,
                            :ExplicitSources => (), :ImplicitSources => ())
context[:WeightConf] = Dict(:name => :exponential, :range => 2.5, :alpha => 1.0)

context[:Domain]  = build_domain(Dict(:domain => :rectangular, :mins => (-1.0,), :maxs => (1.0,), :periodic => true), context)
pg                = build_particle_grid(Dict(:Ns => (200,), :mover => :lagrangian), context)
context[:Flux]    = build_flux(Dict(:name => :Rusanov), context)
context[:Limiter] = build_limiter(Dict(:name => :none), context)
context[:MOOD]    = build_mood(Dict(:criterion => :U2, :strategy => :EPD1, :delta_relax => 1e-4), context)
context[:Scheme]  = build_scheme(Dict(:name => :MUSCL, :order => 3), context)
context[:Tableau] = build_tableau(Dict(:stepper => :RK3), context)
ts                = build_timestepper(context)
adaptivity        = build_adaptivity(Dict(:enabled => true), context)

Every builder is build_x(conf::Dict, context::Dict) and dispatches on Val(conf[:name]) (or the namespace's selector key). Adding a variant means defining one more method:

HyperCloudCore.build_flux(::Val{:HLL}, conf::Dict, context::Dict) = MyHLLFlux()

The physics side is deliberately not here: PDEs, initial conditions and source terms are built by the wrapper, which then fills context[:Equation], [:D], [:M] and the source tuples before calling the builders.

Reference

HyperCloudCore.real_type — Method
real_type(context) -> DataType

The floating-point type of the run: context[:T], or the legacy key context[:Type], else Float64.

source
HyperCloudCore.storage_type — Method
storage_type(context) -> Type

The array type the run lives on: context[:Storage], else Array. With a device array type (e.g. ROCArray) the grid builder returns a device_grid and the scheme and time stepper builders allocate their buffers there (see docs/src/gpu_roadmap.md).

source
HyperCloudCore.SinusoidalVelocity — Type
SinusoidalVelocity{D, T}(A, mins, Ls)

w_d(x) = A sin(2π (x_d - mins_d) / Ls_d): the velocity field of the :sinusoidal mover. A bits-type callable (a closure capturing T or D as values would not be isbits and could not enter a GPU kernel).

source
HyperCloudCore.build_particle_grid — Method
build_particle_grid(grid_conf, context) -> ParticleGrid

Requires real_type(context), [:D], [:M], [:Domain], [:WeightConf]. Stores :max_dx in the context, builds the weight function, the grid mover and the volume estimator from the same Grid namespace, and sets context[:Grid]. The grid is built on the host and moved to storage_type(context) with device_grid if that is not Array.

source
HyperCloudCore.build_tableau — Method
build_tableau(time_conf, context) -> IMEXButcherTableau

Selector :stepper: :Euler, :RK2 (SSP), :RK2Ralston, :RK3 (SSP), :RK4, :ARS222, :ARS233, :PRSSP3, :SSP332, :IMEXEuler. Explicit tableaus are returned as IMEXButcherTableaus with a zero implicit part.

source
HyperCloudCore.build_timestepper — Method
build_timestepper(context; time_conf = Dict()) -> GeneralRKTimeStepper

Requires context[:Equation], [:Scheme], [:MOOD], [:Tableau], [:ExplicitSources], [:ImplicitSources]. Optional Time keys: reset_orders_per_stage, full_search_per_stage; the volume estimator comes from context[:VolumeEstimator] if set (otherwise the stepper default), the stage buffers live on storage_type(context). With context[:MemoryLimit] (bytes) the buffers of the grid, the scheme and the stepper are reserved under that limit (reserve!, with the optional context[:MemoryTolerance] and context[:SlotsPerParticle]); the reservation is stored in context[:Memory].
